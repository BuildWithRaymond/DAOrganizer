# Current architecture and agent boundaries

DA Organizer is a .NET 10 Avalonia Windows desktop app for browsing Dark Ages items across characters and performing reviewed, protocol-confirmed inventory/bank operations. This map describes current code; [the existing architecture note](../ARCHITECTURE.md) and [getting started](../GETTING_STARTED.md) cover behavior and limits. Source wins when documentation and code differ.

```text
MainWindow (Avalonia)
  -> Organizer (sessions, operations, demo guard)
     -> AccountCatalog / InventoryStore (SQLite snapshots, settings, metadata)
     -> Core plans and queues (pure decisions)
     -> GameSession (tracked state, confirmation, Arbiter proxy)
        <-> organizer-launched Darkages.exe <-> game server
```

`src/DAOrganizer.App` references Game and Core transitively; `src/DAOrganizer.Game` references Core and vendored Arbiter; Core has no UI/native dependency. [Solution](../../DAOrganizer.slnx), [project files](../../src/DAOrganizer.App/DAOrganizer.App.csproj), and [CI](../../.github/workflows/build.yml) define the build graph.

## Systems and extension points

| System | Responsibility and data flow | Extend here; avoid duplicating |
| --- | --- | --- |
| App composition and UI | [`Program.cs`](../../src/DAOrganizer.App/Program.cs) / [`App.cs`](../../src/DAOrganizer.App/App.cs) create `Organizer` and `MainWindow`. [`Organizer.cs`](../../src/DAOrganizer.App/Organizer.cs) owns store, sessions, cancellation and demo guard. [`MainWindow*.cs`](../../src/DAOrganizer.App/MainWindow.cs) renders collection, inventory, accounts, storage, organization and action dialogs from that state. | Add a UI surface in the relevant `MainWindow` partial, call existing organizer/Core APIs, and retain `RunOperation` for live work. Avoid direct packet or SQLite access from UI. |
| Profiles and snapshots | [`InventoryStore.cs`](../../src/DAOrganizer.Core/InventoryStore.cs) opens SQLite, migrates schema, stores items/snapshot freshness/settings, and serializes `Item` records from [`Contracts.cs`](../../src/DAOrganizer.Core/Contracts.cs). `GameSession` observations save complete inventory/equipment/bank snapshots; incomplete/stale states remain explicit. | Add schema changes through versioned migration and tests. Extend `InventoryStore` partials for related persistence. Avoid a second profile store or treating cached bank data as live. |
| Character/account and storage settings | [`AccountCatalog.cs`](../../src/DAOrganizer.Core/AccountCatalog.cs) fronts [`InventoryStore.Accounts.cs`](../../src/DAOrganizer.Core/InventoryStore.Accounts.cs): display/update selection, game-account membership, coexistence, storage roles/rules, middleman capability. [`MainWindow.Accounts.cs`](../../src/DAOrganizer.App/MainWindow.Accounts.cs) and [`MainWindow.Storage.cs`](../../src/DAOrganizer.App/MainWindow.Storage.cs) edit these. Optional secrets go through [`CredentialVault.cs`](../../src/DAOrganizer.Game/CredentialVault.cs). | Reuse account catalog/store rules and keep passwords outside SQLite. Do not infer coexistence from account names. |
| Collection, categories and item intelligence | [`ItemMaintenance.cs`](../../src/DAOrganizer.Core/ItemMaintenance.cs) defines exact item key and explicit Keep/Junk/Auto-deposit rules. [`ItemCategoryResolver.cs`](../../src/DAOrganizer.Core/ItemCategoryResolver.cs), [`ItemCategories.cs`](../../src/DAOrganizer.Core/ItemCategories.cs), and [`InventoryStore.Intelligence.cs`](../../src/DAOrganizer.Core/InventoryStore.Intelligence.cs) resolve explicit/legacy/canonical/community categories and local metadata/evidence. [`MainWindow.Items.cs`](../../src/DAOrganizer.App/MainWindow.Items.cs) displays collection/detail; [`ItemImages.cs`](../../src/DAOrganizer.App/ItemImages.cs) reads installed sprites. | Keep one identity key and category precedence. Add metadata via Core/store and use existing resolver in views and plans. Never bundle game sprites or turn uncertain community data into verified facts. |
| Layout and maintenance | [`SlotPlanner.cs`](../../src/DAOrganizer.Core/SlotPlanner.cs) and [`PotionSlots.cs`](../../src/DAOrganizer.Core/PotionSlots.cs) calculate inventory layouts while respecting explicit pins. `MainWindow` previews; [`GameSession.Actions.cs`](../../src/DAOrganizer.Game/GameSession.Actions.cs) applies confirmed swaps. `MaintenancePlan` filters protected items; `MaintenanceRunner` coordinates action; [`GameSession.Maintenance.cs`](../../src/DAOrganizer.Game/GameSession.Maintenance.cs) sends and confirms drops/deposits/withdrawals. | Keep plans and UI review separate from effects. Retain exact slot identity, cancellation, confirmed state changes and no automatic retry of an unconfirmed destructive action. |
| Account updates and travel | [`Organizer.Accounts.cs`](../../src/DAOrganizer.App/Organizer.Accounts.cs) uses [`AccountUpdateQueue.cs`](../../src/DAOrganizer.Core/AccountUpdateQueue.cs) for sequential selected-character updates. [`GameSession.Login.cs`](../../src/DAOrganizer.Game/GameSession.Login.cs) and [`ClientLauncher.cs`](../../src/DAOrganizer.Game/ClientLauncher.cs) handle owned client login. [`WorldGraph.cs`](../../src/DAOrganizer.Core/WorldGraph.cs), [`BankRoutes.cs`](../../src/DAOrganizer.Core/BankRoutes.cs), and [`Navigation.cs`](../../src/DAOrganizer.Game/Navigation.cs) use user WorldLogs for travel. Bank read uses a nearby NPC; transfers need travel. | Reuse queue policy and owned-client lifecycle. Keep failure/cancel cleanup and leave an unsuccessful client available for review. Do not launch/attach arbitrary clients or build a second pathfinder. |
| Proxy and observations | [`GameSession.cs`](../../src/DAOrganizer.Game/GameSession.cs) hosts Arbiter proxy, single-reader observation queue, tracked live inventory/equipment, and snapshot flush. Its partials cover bank dialogue, movement, logout and actions. [`vendor/Arbiter`](../../vendor/Arbiter) supplies packet codecs, proxy, native interop and image readers. | Decode at Game/vendor boundary; expose confirmed state to App/Core. Packet edits need synthetic regression tests and vendor attribution in [`THIRD_PARTY_NOTICES.md`](../../THIRD_PARTY_NOTICES.md). Avoid another proxy, another live state cache, or assumptions from packet send alone. |
| Organization preview, exact approval contract and manual trade evidence | [`InventoryStore.Organization.cs`](../../src/DAOrganizer.Core/InventoryStore.Organization.cs) reads organization inputs in one SQLite transaction and fingerprints them. [`OrganizationPlanner.cs`](../../src/DAOrganizer.Core/OrganizationPlanner.cs) builds read-only opportunities and bounded, non-ready exact candidates. [`OrganizationContracts.cs`](../../src/DAOrganizer.Core/OrganizationContracts.cs) and [`InventoryStore.Plans.cs`](../../src/DAOrganizer.Core/InventoryStore.Plans.cs) define/persist exact steps and stale-checked approval; schema v3 backs up v2 first. [`MainWindow.Organization.cs`](../../src/DAOrganizer.App/MainWindow.Organization.cs) still shows the read-only preview. [`ManualTradeTrace.cs`](../../src/DAOrganizer.Game/ManualTradeTrace.cs), [`ManualTradeAnalyzer.cs`](../../src/DAOrganizer.Game/ManualTradeAnalyzer.cs), and [`Organizer.TradeCapture.cs`](../../src/DAOrganizer.App/Organizer.TradeCapture.cs) support opt-in local observation of a manual two-session trade. | Exact candidates are not wired to approval UI, bank/inventory free-slot capacity is absent from state, and no exchange executes. Manual captures lack proven final-close evidence, so analyzer cannot return `Verified`. See [Phase 1 contract](../handoffs/phase1-organization-contract.md). Keep unknown route/quantity/custody states explicit. |
| Demo, styles and checks | [`DemoCollection.cs`](../../src/DAOrganizer.App/DemoCollection.cs) seeds isolated in-memory data. [`Styles.axaml`](../../src/DAOrganizer.App/Styles.axaml), [`Ornaments.cs`](../../src/DAOrganizer.App/Ornaments.cs) and [design notes](../design/black-and-gold.md) define UI language. Demo screenshots must use fictional data. Preserve 12-column game inventory and existing interaction/scroll behavior. |

## Setup and validation for a fresh agent

Use Windows plus SDK version from [`global.json`](../../global.json). Restore and build from repo root:

```powershell
dotnet restore DAOrganizer.slnx -m:1
dotnet build DAOrganizer.slnx -c Release --no-restore -m:1 -p:UsedAvaloniaProducts=
dotnet test tests/DAOrganizer.Tests -c Release --no-build -m:1
dotnet tests/DAOrganizer.UiChecks/bin/Release/net10.0/DAOrganizer.UiChecks.dll artifacts/ui-checks
dotnet tests/DAOrganizer.UiChecks/bin/Release/net10.0/DAOrganizer.UiChecks.dll artifacts/gallery --gallery
```

Build is also the C# compile/type check; no separate linter is configured. Run `dotnet run --project src/DAOrganizer.App -c Release --no-build -- --demo` to inspect the app without real accounts. [Package script](../../tools/Package.ps1) publishes a self-contained Windows x64 app. NuGet restore needs package-network access on a fresh machine. Demo and synthetic checks need no server, game files, database setup, credentials, or environment variables. Live features need supported Windows game client, user-owned WorldLogs for travel, and optional saved credentials. `DAORGANIZER_DATA_DIR` isolates a development profile; `DAORGANIZER_GAME_DATA` is an optional demo sprite source. SQLite migrations run when a profile opens; there is no separate migration command. See [CI](../CI.md) and [getting started](../GETTING_STARTED.md).

## Parallel work boundaries

Core item metadata/planning, account/storage UI, Game protocol observation, and synthetic tests can be separate tasks after shared records and behavior contracts are settled. `Contracts.cs`, `InventoryStore` schema/migration, `Organizer`, `MainWindow` integration, and vendored packet types are shared hotspots. Assign one owner or sequence dependent phases; require each branch to state interface assumptions and tests. A plan that needs an unsettled schema or exchange contract is not independent yet. Use [feature plan template](../plans/FEATURE_TEMPLATE.md) for larger work and [active organization handoff](../handoffs/cross-character-organization.md) for its current gates.
