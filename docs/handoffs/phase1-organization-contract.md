# Phase 1 exact organization contract

Phase 0 baseline: `e1dd6765ac42f5afad1395d05b523b22bd7662a7`; final Phase 1 baseline: `23bee187c1f82110c84f2cf376fadafd3f37de02` on `feature/cross-character-organization`. Phase 1 adds schema v3 and frozen Core records. The existing `OrganizationPlan` and `OrganizationPlanner.Build(OrganizationState)` remain read-only preview; no preview group is implicitly approved or executable.

## Planner output for Cloud Task A

Use `InventoryStore.ReadOrganizationState()` once and return deterministic exact candidates as `ExactOrganizationPlan` / `PlannedOrganizationStep` from `OrganizationContracts.cs`. `InputFingerprint` must be that state’s fingerprint. `CreatedAt` and `ExpiresAt` are explicit UTC instants, with `CreatedAt < ExpiresAt`. Steps use zero-based contiguous `Order`, unique IDs, and `DependsOn` IDs that appear earlier. Use `ImmutableArray` fields and `OrganizationPlanContract.Validate` before saving. `SourceItem` is the observed item instance; `ItemKey` is `ItemGroups.Key(SourceItem)`. `SourceSlot` is exact for `Ready` steps; `Quantity` is exact, positive, and no greater than that source slot’s observed quantity. Multiple source slots require separate steps.

`OrganizationReadiness` is `Unknown`, `NeedsScan`, `ManualOnly`, or `Ready`. Only a plan whose every step is `Ready` may be approved. Route kinds are `Local`, `Direct`, `Middleman`, and `ManualOnly`; route legs are ordered `Withdraw`, `Exchange`, `Deposit`, or `MoveWithinCharacter`, with chained character/location endpoints. `Local` has no exchange; `Direct` has one; `Middleman` has two. Unknown coexistence, capacity, item identity, stack cap or bank slot means a blocker/readiness downgrade, not a guessed `Ready` action. A manual-only plan can be saved for review but cannot be approved as executable.

`ExpectedBefore` and `ExpectedAfter` contain `OrganizationItemExpectation(Character, Location, ItemKey, Slot, Quantity, ItemFingerprint)`. `Slot=null` sums the matching item identity at that location; a supplied `ItemFingerprint` further limits the sum to one item shape. The fingerprint hashes name, sprite, color, durability, maximum durability and observed stackability; it excludes slot, quantity and display category. A `Ready` step must state exact source-slot quantity before and after (decrease equals `Quantity`) and destination item-shape quantity after. Use `OrganizationPlanContract.ItemFingerprint(SourceItem)` for destination expectation. Include destination before and any other relevant state expectations when planning so Phase 4 can verify conservation. Save only exact, defensible candidates; partial or uncertain candidates stay non-ready.

## Persistence and approval

`InventoryStore.SaveOrganizationPlan`, `LoadOrganizationPlan`, `ApproveOrganizationPlan`, `CheckNextOrganizationStep`, and `ConfirmOrganizationStep` are Phase 1 APIs. Schema v3 adds `organization_plans` and `plan_steps`; v2 profiles receive SQLite online backup `<inventory.db>.v2.backup` before migration. v1 backup behavior stays; future schema versions reject. Migration DDL and version bump are one transaction. Malformed saved steps fail closed.

`ApproveOrganizationPlan` holds an immediate SQLite transaction, reads fresh organization state, compares original fingerprint plus first step’s exact source/before expectations, then persists `Approved` and checkpoint state. `CheckNextOrganizationStep` rejects expired or externally changed checkpoints and checks current source/before expectations. It is a preflight observation, not permission to send packets without fresh live checks. After **independent verified evidence** confirms a step, `ConfirmOrganizationStep` compares expected after quantities and item shape, rejects unrelated state changes, and stores the new full-state fingerprint/checkpoint. Next step compares against that checkpoint, so an approved earlier step does not stale its successor. No Game/App code calls this method yet; Phase 4 must add a durable operation journal and live delivery proof before invoking it. A database `Completed` plan only records that approved step expectations were confirmed locally; it must never substitute for game-side recipient and final bank verification.

## Ownership and limits

Cloud A may edit `OrganizationPlanner.cs` and `OrganizationPlannerTests.cs` only, consuming these records and read-only state. It must not edit schema, `InventoryStore*`, `OrganizationContracts.cs`, App or Game. Phase 1 does not implement transfer execution, middleman scheduling, telemetry, API, or updater. Existing preview remains functional while exact candidate generation is developed.
